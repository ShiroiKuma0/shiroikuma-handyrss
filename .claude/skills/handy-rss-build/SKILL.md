# Handy News Reader — rebranded fork build skill

The user maintains a rebranded build of [Handy News Reader](https://github.com/yanus171/Handy-News-Reader) (itself a fork of Flym) on Android. They run it on a Huawei Mate XT (Android 12, no GMS, microG) alongside — if they wish — the official build. Unlike the SimpleX or jidoujisho forks, **this fork fixes no bug**: its only purpose is a clean identity rebrand so the user has an independent, self-signed app that installs side-by-side with the official one and never collides with it on updates.

The customizations live as a single commit on a `custom` branch in the user's GitHub fork; that branch is rebased onto each new upstream release tag. This is the **same git-branch model** as the user's FairEmail, ArcaneChat, and GNU Jami forks (`master`/`main` mirror + `custom` rebased onto release tags), and the user wants all forks unified on it.

## Workflow

Claude works directly on the user's local tree at `~/git/shiroikuma-handyrss`. No patch files, no scripted shell blocks for copy-paste — Claude edits the tree and runs commands as itself. The build-test-confirm-then-push rhythm is preserved.

### The cycle

1. **Edit the tree** on the `custom` branch. Confirm `git status --short` is clean first; if not, `git reset --hard HEAD` (NOT `git checkout -- .` — see Hard rules below).
2. **Show the user the diff** (`git diff`) before doing anything else. That is the review point.
3. **Build gate.** Wait for the user's explicit go-ahead before invoking gradle. The build then: bumps the counter at `$HOME/.handyrss_build_no`, stamps `versionName 1.1.4+N` / `versionCode 3390000+N` into `FlymFork/build.gradle`, runs `./gradlew :FlymFork:assembleFdroidRelease` with the keystore params, filters output through the NOISE regex (suppresses harmless JP-locale javac + AGP deprecation noise without hiding real errors), and copies the APK to `~/tmp/shiroikuma-handyrss_1.1.4+N_arm64-v8a.apk`. See the Build section for the canonical commands + NOISE regex.
4. **Deliver automatically — no prompt.** After the build + local `~/tmp/` copy, invoke the global **`/after-build`** skill: it runs `/adb-check` (UNSANDBOXED — a sandboxed check falsely reports no device), then `/adb-push` to `/sdcard/tmp/` if the phone is connected, otherwise `/scp` to `skhw:~/tmp/`, announcing what landed. Never ask "Deploy to the Mate XT?" or whether to transfer — `/after-build` decides and acts on its own. Never `adb install` / `adb uninstall` — the user installs via the file manager. (The build itself does not need the phone; the `~/tmp/` copy in step 3 always happens, so the APK exists whether or not the phone is connected.)
5. **User tests on-device.** If there are issues, loop back to (1). A failed build still consumes a counter increment — never reuse a `+N`.
6. **Push gate.** ONLY after the user explicitly confirms ("Push" / "good" / "confirmed"): `git add -A`, descriptive commit message, `git push origin custom`, then sync (`git fetch origin --tags && git pull --rebase origin custom`).

### Hard rules

- **Deliver to the phone automatically via `/after-build` — no prompt.** Building and copying to `~/tmp/` happens once the build is approved; delivery then follows automatically. After a successful build, invoke the global **`/after-build`** skill (which `/adb-check`s UNSANDBOXED, then `/adb-push`es to `/sdcard/tmp/` if the phone is connected, else `/scp`s to `skhw`, announcing what landed) without asking. This supersedes the old "ask with a y/n prompt before adb push" rule — 白い熊's new policy is auto-delivery, no transfer prompt.
- **Never commit/push without on-device confirmation.** The build-test-confirm-then-push cycle is non-negotiable. Builds are not commits.
- **Every build bumps the counter, even failed ones.** Counter file at `$HOME/.handyrss_build_no`, OUTSIDE the repo, so it survives `git reset --hard HEAD` and is never committed.
- **`git reset --hard HEAD` to clean the tree, NOT `git checkout -- .`.** Lesson (D2a push, 2026-05-24): a push aborted at the commit prompt left the change staged in the index; the next attempt's `git checkout -- .` restored the working tree *from the index* — already-patched — and the next `git apply` failed with "patch does not apply" because it was applying on top of itself. `git reset --hard HEAD` clears both index and working tree to HEAD and leaves the untracked Gradle build cache intact. `git status --short` should be empty after the reset.
- **Edits must NOT touch `versionName` / `versionCode`.** The build step owns the version stamp.
- **Post-push sync** (`git fetch origin --tags && git pull --rebase origin custom`) after every push. No-op when in sync; protects against drift, especially after the upstream-rebase force-pushes.

## Versioning (App Manager `+N` scheme — auto-bumped on EVERY build)

The fork uses the same version scheme as the user's other rebranded forks (e.g. 白い熊 App Manager): keep the upstream version and append a monotonically increasing `+N` build tail, so every sideloaded build installs as an *upgrade* (never a downgrade) and never collides with the official app.

- **`versionName` = `<upstream versionName>+<N>`**, **`versionCode` = `<upstream versionCode> × 10000 + N`** — upstream `1.1.4` / `339` → `1.1.4+1` / `3390001`, `1.1.4+2` / `3390002`, … (last four digits = build number; mirrors App Manager's `445 → 4450021` for `4.0.5+21`).
- **EVERY build bumps `N`. No exceptions. Never reuse a number** — even a rebuild of the same unpushed feature gets the next `+N`. (An earlier version of this skill wrongly said iterations could keep the same `+N`; that caused repeated `+1` collisions and was the cause of a real complaint. It is deleted — do not reintroduce it.)
- **The build step owns the version; feature edits are version-agnostic.** Edits to `build.gradle` for other reasons (e.g. the `buildconfig` fix) are fine, but the `versionName` / `versionCode` lines must NOT be touched at edit time. The version is stamped at build time from the persistent counter at `$HOME/.handyrss_build_no` (deliberately outside the repo so it survives `git reset --hard HEAD` and never enters a commit). Each build: read the counter, increment, write back, then update the `defaultConfig` lines in `FlymFork/build.gradle` to `versionName '1.1.4+N'` and `versionCode 3390000+N`. Only the `defaultConfig` lines — the `applicationVariants` `def versionName = variant.versionName` / `def versionCode = variant.versionCode` lines are derived and must be left intact. The APK is named `shiroikuma-handyrss_1.1.4+N_arm64-v8a.apk`.
- **Push commits the last-built version, not a fresh increment.** After on-device confirmation, re-read the counter **without** incrementing, stamp that `versionName` / `versionCode` into `build.gradle`, and commit it with the feature, so the pushed commit carries the exact version of the APK that was tested.
- **On an upstream rebase:** update the two base literals (`1.1.4` → new upstream `versionName`, `3390000` → new `<upstream versionCode> × 10000`) wherever they live in the skill text + the project, and **reset the counter** with `rm -f $HOME/.handyrss_build_no` so the first build of the new upstream is `+1`.
- The **APK filename derives from the stamped `versionName`** (`shiroikuma-handyrss_<versionName>_arm64-v8a.apk`), self-documenting the build number; no datetime stamp.

## Why this fork exists — and why the provider authorities matter

The user wants their own signed Handy News Reader that coexists with the official one. Changing only `applicationId` is **not sufficient** for side-by-side install: Handy News Reader declares two `ContentProvider` authorities and one custom permission that are hardcoded (not derived from `${applicationId}`), and Android refuses to install a second app that declares a content authority already owned by an installed app. So the rebrand must change the authorities too — consistently in both the manifest AND the code, or the app's own provider lookups break.

The saving grace: **both code-side authorities derive from a single constant.** In `FlymFork/src/main/java/ru/yanus171/feedexfork/provider/FeedData.java`:

```java
public static final String PACKAGE_NAME = "ru.yanus171.feedexfork";          // line ~78
public static final String AUTHORITY = PACKAGE_NAME + ".provider.FeedData";   // line ~80
```

and in `FlymFork/src/main/java/ru/yanus171/feedexfork/utils/FileUtils.kt` (line ~410):

```kotlin
FileProvider.getUriForFile(MainApplication.getContext(), FeedData.PACKAGE_NAME + ".fileprovider", file)
```

So changing the one `PACKAGE_NAME` literal cascades to BOTH the `…provider.FeedData` and `…fileprovider` authorities in code. The manifest's four hardcoded strings then just need to match.

**`PACKAGE_NAME` is NOT the Java package / namespace.** The Kotlin/Java namespace stays `ru.yanus171.feedexfork` (changing it would break every `import ru.yanus171.feedexfork.*` in 117 source files). `PACKAGE_NAME` is only ever concatenated into authority strings — it is safe and correct to repoint it at `shiroikuma.handyrss`.

## The customizations (the `custom` branch commit)

Five edits. Four are in-tree (committed on `custom`); the fifth is a deploy-time rename. These seds are the **canonical definition** of what the `custom` branch commit contains — if a rebase ever conflicts (upstream moved one of these lines), regenerate the commit from a clean tag by re-running them.

1. **`applicationId`** in `FlymFork/build.gradle` (line ~13): `ru.yanus171.feedexfork` → `shiroikuma.handyrss`. **Leave `namespace 'ru.yanus171.feedexfork'` (line ~96) untouched.**

2. **`PACKAGE_NAME`** in `FlymFork/src/main/java/ru/yanus171/feedexfork/provider/FeedData.java` (line ~78): `"ru.yanus171.feedexfork"` → `"shiroikuma.handyrss"`. Cascades to both code-side authorities.

3. **Manifest authorities + permission** in `FlymFork/src/main/AndroidManifest.xml` (lines ~17, 64, 66, 69): repoint the `ru.yanus171.feedexfork.provider.*` / `.fileprovider` strings to `shiroikuma.handyrss.*` so the manifest matches the code. Four occurrences:
   - permission declaration `android:name="ru.yanus171.feedexfork.provider.WRITE_PERMISSION"`
   - FeedData provider `android:authorities="ru.yanus171.feedexfork.provider.FeedData"`
   - FeedData provider `android:writePermission="ru.yanus171.feedexfork.provider.WRITE_PERMISSION"`
   - FileProvider `android:authorities="ru.yanus171.feedexfork.fileprovider"`
   A single global sed of `ru.yanus171.feedexfork.provider` → `shiroikuma.handyrss.provider` plus `ru.yanus171.feedexfork.fileprovider` → `shiroikuma.handyrss.fileprovider` handles all four. **Do NOT** sed bare `ru.yanus171.feedexfork` in the manifest — that would corrupt `android:name=".MainApplication"`-style relative names is not at risk, but the `.provider`/`.fileprovider`-qualified seds are precise and sufficient; keep them qualified.

4. **App label** — rebrand `app_name` across ALL locales (14 files) so the launcher label and in-app name show `白い熊 Handy RSS` regardless of device locale. The launcher activities `HomeActivity` and `HomeActivityNewTask` bind `android:label="@string/app_name"`, and `app_name` is defined in `res/values/strings.xml` plus `res/values-*/strings.xml`. One regex sed over the glob rebrands them all and survives upstream pulls:
   ```
   sed -i -E 's#<string name="app_name">[^<]*</string>#<string name="app_name">白い熊 Handy RSS</string>#' FlymFork/src/main/res/values*/strings.xml
   ```

5. **APK naming + version** — the build's `applicationVariants.all` block names the raw output `shiroikuma.handyrss_fdroidRelease_<versionName>_<versionCode>.apk`; we rename it on `cp`/`adb push` to `shiroikuma-handyrss_<versionName>_arm64-v8a.apk` (version-based, no timestamp — derive `<versionName>` by grepping it from `build.gradle`, after the patch is applied in a feature build). The `versionCode`/`versionName` themselves are bumped per the **Versioning** scheme above and committed with each feature — the one gradle edit beyond the rebrand that changes build-to-build.

No ABI / split edit: the `fdroid` flavor pulls no native libraries, so an abiFilter is moot. The APK runs on arm64-v8a (and everywhere else); the `_arm64-v8a` suffix names the deploy target per the established filename grammar.

## Thunderbird-native feeds OPML export (commit 30)

The plain (non-backup) feeds export imports into Mozilla Thunderbird as **foldable categories whose individual feeds are separately readable**. Requirements (verified against TB 140 ESR's import source `feed-subscriptions.js` `importOPMLOutlines`, and its own export format):
- **Per-feed wrapper folders (3 levels):** `category <outline>` → per-feed `<outline>` (folder, no `xmlUrl`) → **self-closing** feed `<outline type="rss" version="RSS" xmlUrl htmlUrl text title/>`. A feed placed *directly* in a category folder is **merged** (all feeds share that folder, not individually readable). Only **grouped** feeds are wrapped (`ExportFeed(..., wrapInFolder)`); root/ungrouped feeds stay plain top-level feed outlines; the **backup** format is unchanged (feeds direct, open+close, with entries).
- Feed outlines must be **self-closing** and carry **both `type="rss"` AND `version="RSS"`** (without `version`, TB treats them as folders), plus `xmlUrl`/`htmlUrl`/`text`/`title` (`OUTLINE_TEXT`, `OUTLINE_FEED_EXTRA` constants).
- **`.opml` extension:** SAF exports use mime `application/octet-stream` (not `text/xml`, which makes the provider append `.xml` → `…opml.xml`, which TB ignores).
- **Round-trip safe:** the importer (`OPMLParser`) uses a folder-nesting **depth counter** (`mGroupDepth`) so only the outermost folder becomes a Handy RSS group; the per-feed wrapper folders collapse and feeds land back in their category.
- Full format + the Thunderbird **testing gotchas** (import only subscribes — articles need Receive; re-importing a URL already subscribed in an account is silently skipped, "0 new"; test in a fresh feed account or delete with "Remove message data") are in the `thunderbird-feeds-opml` auto-memory.

**This increment took ~6 builds to land. Four traps, each now a rule:**

1. **The reading-view menu hides everything then re-shows a whitelist.** `EntryView.onPrepareOptionsMenu` calls `hideAllMenuItems(menu)` and then `setVisible(menu, R.id.…)` only for a hardcoded set of IDs; `WebEntryView.onPrepareOptionsMenu` adds its own `setVisible` list after `super`. **Any new item added to `entry.xml` is invisible (toolbar AND overflow) until you also add `setVisible( menu, R.id.menu_read_… )` to `WebEntryView.onPrepareOptionsMenu`** (right after `super.onPrepareOptionsMenu( menu )`). This is THE reason a freshly-inflated item "doesn't appear anywhere."

2. **`setHtml` has a content-hash guard that blocks CSS-only re-renders.** `WebEntryView.setHtml` computes `content.getContentHash()` (from the article content, NOT the CSS/font prefs) and `if (mLastContentHash != 0 && mLastContentHash == contentHash) return;`. So changing only a font pref and calling `update(true)` → `generateArticleContent` → `setHtml` bails (same hash) and the article does NOT re-render — it only updates on exit/reopen (fresh view has `mLastContentHash == 0`). **Fix: a `public void ForceContentReload() { mLastContentHash = 0; update( true ); }` on `WebEntryView`, called via `GetSelectedEntryWebView()` (returns `WebEntryView` or null) — NOT `GetSelectedEntryView().update(true)`.** `update(true)` → `InvalidateContentCache()` (resets `mContentWasLoaded`, saves scroll pos) + `generateArticleContent()` → `setHtml` (now passes the hash guard) → `loadDataWithBaseURL`. Re-render sliders on `onStopTrackingTouch` (release), not per tick, to avoid WebView thrash.

3. **Insert new methods ABOVE a method's annotations, not between annotation and signature.** `onOptionsItemSelected` is preceded by `@SuppressLint("NonConstantResourceId")` + `@Override`. Anchoring an insert on just `public boolean onOptionsItemSelected(MenuItem item) {` puts the new methods between `@Override` and the signature, so `@Override` then annotates the new (non-overriding) method → `メソッドはスーパータイプのメソッドをオーバーライドまたは実装しません` compile error. Anchor on the full `@SuppressLint(...)\n@Override\npublic boolean onOptionsItemSelected…` block and insert before it.

4. **A new toolbar icon needs the tint baked into the `<vector>`, or it renders black-on-black (invisible).** The chrome recolor tints icons per-drawable, not via a blanket toolbar theme: 86 drawables carry `android:tint="@color/menu_pref_fg"` + `android:alpha="0.8"` on the `<vector>` root (with `fillColor="#FF000000"` on the path). A new icon with only `fillColor="#FF000000"` and no `android:tint` renders solid black → invisible on the black bar (the menu item's slot is still present and tappable — which is the misleading symptom; it looks "missing" but tapping its empty space fires the action). Always copy the `android:alpha="0.8" android:tint="@color/menu_pref_fg"` attributes onto any new icon vector. (This also means a missing/odd-coloured icon is NOT a room problem — verify the tint before theorising about action-bar overflow.)

**`showAsAction` room note:** the reading view comfortably fits these three plus `menu_share`/`menu_search`/`menu_search_next`/`menu_search_previous` as `always`. An earlier detour to `ifRoom` was a red herring (the real bug was the invisible icon): with the existing `always` items consuming the computed `maxItems`, `ifRoom` items get **zero** slots and fall to the overflow, which looked like "all icons disappeared." Keep these three `always`.

## Build lessons (durable)

Technical learnings from the 23 commits — these inform what the Build section actually does.

- **Gate post-build steps on the real gradle exit code** via `PIPESTATUS[0]` (the gradle output is piped through `grep -vE "$NOISE"`, which would otherwise mask gradle's exit status). Without this, a failed build falls through and the next step grabs a stale APK — happened once. Also `rm -f FlymFork/build/outputs/apk/fdroid/release/*.apk` before invoking gradle so a stale leftover can never be mistaken for a fresh one.
- **Warning filtering (NOISE regex).** Pass `--warning-mode none -Pandroid.javaCompile.suppressSourceTargetDeprecationWarning=true`, and pipe gradle through `grep -vE "$NOISE"`. Two non-obvious things the canonical NOISE handles:
  - the user's JDK emits javac warnings in **Japanese** (locale), so the filter targets the JP strings — `(^|m)警告:` + `警告[0-9]+個` (the `[options]` obsolete source/target-8 warnings + the warning-count summary), `(^|m)ノート:` (deprecation notes), `廃止されたオプション`, `推奨されないAPI`, `-Xlint` — not the English forms;
  - `(^|m)` anchors instead of `^` because stderr lines may arrive prefixed with the trailing `m` of an ANSI color escape from the gradle output;
  - aapt `warn: removing resource … without required default value`, the AGP `buildconfig` block (also fixed at the root — see Gotchas), and the Gradle `Deprecated Gradle features were used` / `Problems report is available` summary are also covered.
  Real errors (`エラー:` / `error:`), `BUILD SUCCESSFUL/FAILED`, and `> Task` / `> Configure` lines always pass through unfiltered. The canonical NOISE regex lives in the Build section.
- **apksigner verify noise.** The v1 (JAR) signature legitimately doesn't cover certain `META-INF/` metadata entries (androidx `.version`, `app-metadata.properties`, `README.md`), so `apksigner verify --verbose` prints a wall of "not protected by signature" lines. They are harmless — v2/v3 protect the whole APK, and the Mate XT verifies via v2. Filter with `grep -v "not protected by signature"`. The "real" fix (disable v1 via `v1SigningEnabled false` in `signingConfig.release`) is deliberately not done; v1+v2 is harmless and avoids a committed signing-config change.
- **Resource-collision check.** Before any change that adds `<string>` / `<string-array>` entries, grep the merged resource file for duplicate `name="…"` — aapt fails the resource merge on a redefined resource (hit once: a new `settings_font_size` collided with the app's existing "Text size" string). Reuse the existing resource or pick a unique name.
- **Prefer adding NEW files over rewriting committed ones** when the change is large or risky. A brand-new file has no context to misalign with anything; reduces the chance of breaking an existing surface.

## Configurable fonts architecture (increment 1)

Per-surface fonts (family + weight + size), each surface fully **independent** — there is intentionally **no global "Default" cascade** (the user found a global that silently changes multiple surfaces confusing). Unset → the app-wide font (`fontFamily`) / the caller's existing size, so unset = unchanged behavior.

- **`utils/FontUtil.java`** — resolves per surface from prefs `font_family_<cat>` / `font_weight_<cat>` / `font_size_<cat>`. Family resolves through the EXISTING `FontSelectPreference.GetTypeFaceByName(name)` (so bundled assets fonts AND external fonts in `FileUtils.getFontsFolder()` — `…/fonts/` on /sdcard — work). Weight applies via `Typeface.create(base, w, false)` on API 28+ (else BOLD if ≥600). `apply(TextView, cat, fallbackSizeDip)`: category size (sp) if set, else the caller's original dip size. Cats: `TITLE`, `LIST_TEXT`, `DRAWER`, plus `BODY`/`MENU` reserved for later increments.
- **`view/FontSizePreference.java`** — a custom `Preference` (mirrors `FontSelectPreference`'s self-built `onCreateView`) showing a `SeekBar` + a **live preview** TextView rendered in the surface's actual `FontUtil.typeface(cat)`; persists the sp value as a string (0 = unset). No "sp" jargon shown. This replaced a hand-typed `EditTextPreference` size field the user disliked.
- **Weight UI** is a `ListPreference` (Default/Thin 100/Light 300/Regular 400/Medium 500/SemiBold 600/Bold 700/Black 900 via `@array/font_weight_entries`+`font_weight_values`), not a typed number.
- **Settings → Fonts** screen in `general_preferences.xml`: one group per surface (Article title / Article text in list / Feed-category drawer), each = `FontSelectPreference` + weight `ListPreference` + `FontSizePreference`, ending with a non-selectable empty spacer `<Preference android:selectable="false" android:title=" "/>` so the bottom slider clears the screen-protector edge.
- **`FontSelectPreference` reuses per-instance keys** — it reads/writes via `getPersistedString`/`persistString` (its own `android:key`), so multiple instances with distinct keys each pick independently. ONLY the "Add custom font file" spinner action is hardwired to the global `KEY="fontFamily"` (it imports the file then assigns it globally); so: import a new external font once, then *select* it per surface.
- **Hooks** (replace the surface's `SetFont(tv,1)`): `EntriesCursorAdapter` title (the `SetFont(holder.titleTextView,1)` site) → TITLE; the in-list preview `textPreviewTextView` and inline body `textTextView` (in `SetupEntryText`) → LIST_TEXT; `DrawerAdapter` `titleTxt`/`unreadTxt`/`readTxt` → DRAWER. The legacy cryptic entry-list `fontsize_entrylist` "Text size" ListPreference was REMOVED from the UI (its delta still feeds `getFontSizeEntryList()` as the fallback base).
- **Reading view (BODY + headings) — done via WebView CSS, NOT FontUtil.** The article reading view is HTML in a WebView; its stylesheet is built in `view/WebEntryContent.java` `GetCSS()` (NOT `EntryView.java`, which is abstract). Fonts there are CSS, resolved by reading the `font_*_body` / `font_*_heading` prefs directly (same key scheme as FontUtil, but FontUtil's `Typeface` path is irrelevant for CSS):
  - **BODY** (increment 2): `GetTypeFaceLocalUrl(<font_family_body || global "fontFamily">)` feeds the `@font-face "MainFont"` `src` (a font-file URL, so bundled AND external `/sdcard/.../fonts/` files work); `mainFontSize` (used by body/p/buttons) is overridden to `font_size_body + "pt"` when set, else the legacy `getFontSizeText(0)`; body `font-weight` uses `font_weight_body` (numeric, with trailing `;` to match `getFontBold()`'s format) when set, else `getFontBold()`. Unit caveat: the slider preview is sp but the WebView renders pt — tune by eye.
  - **HEADINGS** (increment 3): `h1`/title take `font_size_heading + "pt"` when set (else `getFontSizeText(4)`), `h2` tracks 2pt smaller to preserve the hierarchy; heading `font-weight` uses `font_weight_heading` else `normal`; when `font_family_heading` is set a `@font-face "HeadingFont"` is emitted and a `title,h1,h2 {font-family:"HeadingFont"}` rule added — when unset, headings keep inheriting `MainFont` (the body font), the original behavior. All three heading rules live consecutively in `GetCSS()` (the `title, h1, h2 {font-weight…}` / `title, h1 {font-size…}` / `h2 {font-size…}` lines) — good, stable anchors.
  - **Removed** the legacy global "Text size" (`AutoSummaryListPreference` key `fontsize`, title `@string/settings_font_size`) from the Article-text settings screen — it overlapped the new BODY size and confused the user. The `fontsize` *pref/getter* (`PrefUtils.getFontSize()`, reads float pref `"fontsize"`) still exists and remains the fallback base for body/headings when a per-surface size is unset; only the UI control was deleted. (Increment 1 earlier removed the *entry-list* `fontsize_entrylist` "Text size" control — two distinct legacy size controls, both now gone from the UI; do not confuse them.)
- **Remaining increment:** MENU (system-drawn option/context menus — hardest; needs a `TypefaceSpan` on menu-item titles or a themed approach, since menu items aren't TextViews we hook directly).

## Co-install crash: stale explicit-intent targetPackage (commit 10)

The fork is **public and co-installed beside the official `ru.yanus171.feedexfork`** on the user's device — that is the whole point of the rebrand (distinct `applicationId` + provider authorities). The bug is invisible until the original app is co-installed — diagnose from logcat (`adb logcat AndroidRuntime:E ...`); the trace names the offending `cmp=` component.

## 白い熊 Handy RSS UI screen — indentation discipline (STRICT)

The screen formerly titled "Fonts" is now **白い熊 Handy RSS UI** (`settings_category_fonts` string; the `prefs_ui_screen` nested `<PreferenceScreen>` in `res/xml/general_preferences.xml`). 白い熊 requires a **strict 3-tier indentation + logical grouping** on it — every item sits at its tier under its logical parent, **no exceptions** (this supersedes the older "~32 dp" numbers in the commit-12 note above). Repeatedly corrected on-device; treat as a hard rule whenever touching this screen.

- **Tier 1 — section header / top-category: 16 dp.** `@layout/preference_font_topcat` (bold yellow + 2 dp underline rule). E.g. "Reading view", "List view", "Left toolbar", "Export / Import".
- **Tier 2 — sub-head: 50 dp** (≈ mid-"a" of the parent header above it). `@layout/preference_font_subhead` (underlined yellow). E.g. "Article text", "Article headings", and the `ExportImportPreference` box titles.
- **Tier 3 — rows / sub-items: 100 dp** (double the sub-head). Sources that must all match: `@layout/preference_font_row` (`paddingStart=100dip`); the two code-built prefs `FontSelectPreference`/`FontSizePreference` (`onCreateView` root `UiUtils.dpToPixel(100)`); `ExportImportPreference` subitems (`leftMargin = dp(100)`, its title at `dp(50)`); and plain `CheckBoxPreference`/`ListPreference` via **`android:layout="@layout/preference_indented"`** (a standard title/summary/`@android:id/widget_frame` row padded to 100 dp — so the checkbox still inflates).
- **Grouping:** a sub-head's children — including config toggles like the auto-backup `enabled`/`interval`/`toast`/`charging` — are tier-3 sub-items of that sub-head and must be indented to 100 dp. A bare `CheckBoxPreference`/`ListPreference` defaults to flush-left (16 dp) and is **wrong** here; always give it `@layout/preference_indented`.
- The **Export / Import** section lives at the **bottom** of this screen (after "Left toolbar"): a tier-1 "Export / Import" header, then three `ExportImportPreference` boxes (settings / RSS channels & feeds / Auto backup), with the auto-backup toggles as tier-3 rows under the Auto-backup box.

## Build

Build the `custom` branch directly — the rebrand commit is on it. AGP signs via `signingConfigs.release` (driven by `-P` properties on the gradle command) and produces a signed, zipaligned release APK in one step — no manual `zipalign` / `apksigner` follow-up. First build pulls a few hundred MB of Gradle/AGP dependencies; subsequent builds finish in a couple of minutes. Working directory is `~/git/shiroikuma-handyrss`, `JAVA_HOME` must point to OpenJDK 21 at `/usr/lib/jvm/java-21-openjdk-amd64`.

```
    -Pandroid.javaCompile.suppressSourceTargetDeprecationWarning=true
```

Pipe stderr+stdout through `grep -vE "$NOISE"` (regex below). Capture gradle's REAL exit code via `${PIPESTATUS[0]}` — `grep` succeeds even on a failed build, so the unfiltered status is what determines success. Before invoking gradle, **clear any stale APK** from `FlymFork/build/outputs/apk/fdroid/release/` so a leftover can't be mistaken for a fresh build.

**On success.** The APK lands in `FlymFork/build/outputs/apk/fdroid/release/` (release-flavor naming, single file after the pre-build cleanup). Copy it to `~/tmp/shiroikuma-handyrss_<versionName>_arm64-v8a.apk` — this local archive happens unconditionally, BEFORE any phone interaction, so the user always has the APK whether or not the phone is connected.

**Deliver (automatically — no prompt).** Once a build succeeds, invoke the global **`/after-build`** skill: it runs `/adb-check` (UNSANDBOXED — a sandboxed check falsely reports no device), then `/adb-push` to `/sdcard/tmp/<same-name>` if the phone is connected, otherwise `/scp` to `skhw:~/tmp/`, announcing what landed. No "Deploy now?" question, no "phone connected?" prompt. The user installs the APK manually via the file manager — never `adb install` / `adb uninstall`. Updates over a previous `shiroikuma.handyrss` build install cleanly because the keystore is stable. The custom build coexists with the official Handy News Reader because applicationId AND all content-provider authorities differ (edits 2 + 3).

## Update procedure (every upstream release) — rebase `custom`

The git-branch model, identical to the FairEmail / ArcaneChat / Jami forks.

1. Fetch upstream: `git fetch --tags upstream`. Identify the new latest tag **by date** (NOT lexical order — the ancient Flym `v1.8.0`/`v1.9.4` tags sort to the top but are 2016 code):
   ```
   git for-each-ref --sort=creatordate --format='%(creatordate:short) %(refname:short)' refs/tags | tail
   ```
2. Fast-forward the mirror: `git checkout master && git merge --ff-only upstream/master`.
3. Rebase the customization commit onto the new tag:
   ```
   git checkout custom
   git rebase --onto <new-tag> <old-base-tag> custom
   ```
   The four edits sit on stable, low-churn lines, so this normally replays cleanly.
4. **If the rebase conflicts** (upstream moved one of the four edit sites): abort (`git rebase --abort`), recreate `custom` from the new tag (`git checkout -B custom <new-tag>`), and re-apply the four edits from the "Original rebrand procedure" section above + commit. The four mappings are the canonical definition of the commit — trust them over resolving a fiddly conflict by hand.
5. Verify the four edits are present (re-read each target file). This is also where you would notice an upstream refactor that obsoletes an edit — e.g. if `PACKAGE_NAME` ever becomes `BuildConfig.APPLICATION_ID`, edit 2 becomes unnecessary and edit 3 can switch to `${applicationId}`-qualified manifest authorities.
6. **Reset the version tail** for the new upstream version in `FlymFork/build.gradle`: `versionName` → `<new upstream versionName>+1`, `versionCode` → `<new upstream versionCode> × 10000 + 1` (read the new upstream `versionCode` from the rebased `build.gradle` first). Then force-push: `git push -f origin custom`, then **sync**: `git fetch origin --tags && git pull --rebase origin custom`. Optionally tag the snapshot: `git tag shiroikuma-v<new> && git push origin shiroikuma-v<new>`.
7. Build (see Build section) and deploy.

## Gotchas

- **`buildConfig` build feature (root-fixes the AGP buildconfig deprecation warning).** The fork enables BuildConfig the module way — `buildFeatures { buildConfig true }` in `FlymFork/build.gradle`, inside `android {}` right after `defaultConfig` — and **removes the deprecated global `android.defaults.buildfeatures.buildconfig=true` from the root `gradle.properties`**. AGP 8.9 warns that the gradle.properties default is deprecated (default is now `false`); this silences it at the source while keeping BuildConfig generated (the app references it). On an upstream rebase, keep BOTH: the module `buildFeatures{ buildConfig true }` present and the gradle.properties default absent — they travel on the `custom` commit. This is the one warning fixed at root rather than filtered (all others are filtered via NOISE).
- **Never change `namespace`** — only `applicationId` and `PACKAGE_NAME`. The namespace is the Java package used by 117 source files.
- **`PACKAGE_NAME` is the authority root, not a display string.** If upstream ever refactors `FeedData.PACKAGE_NAME` to read `BuildConfig.APPLICATION_ID`, then changing `applicationId` alone cascades everywhere and edit 2 should be dropped while edit 3 switches the manifest to `${applicationId}`-qualified authorities. Re-verify on each major version.
- **`fdroid` flavor, not `full`.** `full` pulls `com.google.android.gms:play-services-safetynet` and a PDF viewer; SafetyNet is pointless and broken on a microG device. Build `:FlymFork:assembleFdroidRelease`.
- **Unsigned APK symptom:** if the release APK comes out unsigned, the `-P` keystore properties were not passed or the keystore path is wrong — the gradle `signingConfigs.release` is gated on `project.hasProperty("KEYSTORE_PATH")`.
- **Gradle wrapper download timeout (first build of a new Gradle version):** the fork pins its Gradle version in `gradle/wrapper/gradle-wrapper.properties` (1.1.4 → `gradle-8.11.1-bin.zip`). The wrapper's built-in downloader has a short read-timeout and fails on the ~130 MB fetch with `SocketTimeoutException: Read timed out`. Remedy: download the zip out-of-band and seed the wrapper cache — `wget -c --tries=20 --timeout=120 -O ~/tmp/gradle-<ver>-bin.zip https://services.gradle.org/distributions/gradle-<ver>-bin.zip`, then copy it to `~/.gradle/wrapper/dists/gradle-<ver>-bin/<hash>/gradle-<ver>-bin.zip` (the `<hash>` dir is created by the failed attempt, or trigger it with `timeout 25 ./gradlew --version`) and `rm` any stale `*.ok` marker there. The wrapper then skips its own download and unzips the seeded copy. No `distributionSha256Sum` is pinned, so a hand-downloaded zip is accepted. This recurs whenever an upstream bump changes the pinned Gradle version.
- **`aapt dump badging`:** invoke a single resolved binary — `AAPT=$(ls -1 $ANDROID_HOME/build-tools/*/aapt | sort -V | tail -1)` then `"$AAPT" dump badging <apk>` — never a bare `build-tools/*/aapt` glob (it expands to multiple paths and the extra ones become bogus arguments). Use it only against a real built APK to confirm `package: name='shiroikuma.handyrss'` (the applicationId the OS keys on).
